This turns the Week 1 prototype into the loop Kay described: report, route, track, verify. Nothing here is built yet. Review it, change it, and then we build from it.

What this plan assumes, and what it doesn't know
  • It follows Kay's answers: a dashboard checked manually to start with, the authority reports completion and then the public or AI verifies it, and the data must be UK-compliant.
  • Hour estimates are rough guesses (about ±50%). They assume around 10 hours a week on Resolve UK, because development time is shared with Celestial Companions.
  • Service prices, licence terms and which council handles what come from memory. Check them before committing to anything.

Submitting a report

Compared with the prototype, this adds a nearby-report check, photo shrinking, a history entry, automatic routing and an AI suggestion.

  • Nearby check: same issue type, still open, within a set distance. Start at roughly 10–20 m for potholes and 25–50 m for the rest, always above typical GPS error. The distances get tuned with real data.
  • Routing rule: the authority whose boundary contains the point and whose responsibilities include this issue type. This handles two-tier areas, where the county handles potholes and the district handles fly-tipping.

Verifying a fix

The AI assists and never decides alone. Its answers are "likely resolved", "potentially unresolved" or "needs human review".

Reports that stay "Cleared" with nobody confirming them still count, but as unverified. That keeps the verification rate honest.

How the data flows

Data model

The key change from the prototype: a report's history is a list of entries that only ever grow. The current status becomes a shortcut copied from the latest entry, not the source of truth.

What changes in the current prototype

  • Issue types grow from three to five: fly-tipping, potholes, graffiti, abandoned vehicles, damaged infrastructure.
  • The form records GPS accuracy, and photos are shrunk before upload and stored by path.
  • Submitting also writes the first history entry. The list shows the status timeline instead of a single word.
  • New: staff sign-in and the dashboard. The Supabase keys move to the new London project.

Decisions needed

  • Who runs the dashboard first? The Resolve team acting for councils, or council staff. The design supports both, but it changes who gets accounts. Blocks 2C.
  • Are photos public straight away, or checked first? Photos can show faces and number plates. Blocks 2B.
  • Anonymous or accounts for citizens? A device token is simpler but easier to game when counting "same issue" confirmations. Affects 2B.
  • Verification thresholds. How many confirmations, how confident the AI must be, and what happens if nobody responds. Affects 3.
  • Retention. How long reports and photos are kept. Needs the compliance advice mentioned earlier. Affects 2A.
  • Pilot authority. Which council, and which responsibilities it covers. Huddersfield (Kirklees) was suggested as the simplest, subject to checking. Affects 3.
  • Which project comes first. Resolve UK or Celestial Companions. Sets the real timeline.

Handover checklist

  • Accounts (Supabase, Vercel, GitHub) sit in organisations that can be handed over by adding the new owner, not by sharing a password. Two-factor sign-in is on.
  • The database structure lives in the repo as migration files, so the whole database can be recreated in any region or account.
  • The README lists every environment variable, how to deploy, and how to rotate keys. Secrets live in each platform's secret store, never in chat or email.
  • Backups are decided on purpose. The free tier may not include them, so confirm before real data arrives.
  • A list of every third-party service used, with what it costs and who pays.
